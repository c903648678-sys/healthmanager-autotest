# 集成测试设计模板

- 集成测试设计模板
  - 风险
    - 风险识别标准：体现特性“在什么场景下”导致的“失效情况”、“失效的概率”和“失效的影响”：正确识别风险，不要将风险、障碍、自身理解问题三者混为一谈
    - 风险举例
      - 主要针对质量的风险，如某个场景的质量，在当前的覆盖下存在交付质量的风险
  - 障碍
    - 障碍识别标准
      - 阻碍测试人员开展正常活动的因素，或者使效率变慢的因素。
    - 障碍分类举例
      - 1、输入（需求描述不清晰、缺少设计规格、缺少需求背景、缺少资料）
        - 举例
          - 障碍例子描述
            - 在需求分析阶段，未输入需求的相关规格，导致测试设计的输入有限，会影响测试覆盖
          - 应对的方式 
            - 开发、测试、需求的原始提出人需要基于对需求的详细的分析，进行充分的需求讨论，形成理解一致的需求澄清和策略 
      - 2、时间（转测试延期、测试时间不充分）
        - 举例
          - 障碍例子描述
            - 紧急特性，特性发布需要1天内完成，但是测试场景无法完成全量覆盖
          - 应对策略
            - 1、与开发、架构师、产品经理等完成策略对齐，是否认可紧急特性测试策略
            - 2、优先完成核心场景测试
            - 3、未完成的场景在特性上线后继续测试
              - 研发区继续测试并形成自动化看护
              - 基于现网完成剩余场景测试
              - 存在问题修复后补丁升级验证
      - 3、方法（测试不成熟、新技术的掌握程度较差）
      - 4、环境（测试环境冲突、单板资源不足、测试机不满足、环境版本不具备）
  - 背景
    - 项目信息
      - 工具、自动化有哪些新诉求？
      - 对于环境有哪些特殊要求？
      - 需要提前储备哪些技能/知识？
      - 和周边微服务有哪些配合诉求？
    - 需求背景
      - 服务站点
        - 中国站
        - 国际站
      - 原始需求
        - 需求号&需求名称
      - 需求文档路径
        - 规格路径&规格章节
        - 高低保真路径
  - 测试计划
    - 版本计划
      - 交付哪个版本？
      - 集成测试完成时间
      - 是否需要场景级E2E测试
    - 阶段计划
      - 阶段一
      - 阶段二
      - 阶段三
      - ...
  - 测试分析
    - 用户操作
      - 谁会使用？
        - 哪些类型的用户会使用？
          - 未注册用户
          - 普通注册用户
          - 同时存在多身份的用户
          - 用户的限制状态
        - 哪些地方的用户会使用？
          - 是否涉及多地域用户的操作？
      - 用户如何使用？
        - 用户通过什么渠道使用？
          - 通过前台使用？
          - 通过后台使用？
        - 操作前用户能够看到什么数据？
        - 用户的操作步骤是什么？
        - 用户操作过程中和操作后，能够看到什么数据？用户的数据是否涉及个人隐私敏感数据？
        - 操作后，用户能够获得什么？
        - 用户会收到短信/邮件通知吗？
      - 生命周期中是否会有后续操作？
      - 涉及并发操作的可能性从而导致数据异常吗？
    - 实现逻辑
      - 为了实现该对象，系统做了什么？
      - 业务流程是什么？业务从哪里入口？
        - 对应什么菜单？什么按钮？
        - 对应什么接口？
      - 业务流程中，各部件在流程每个点的处理逻辑
    - 操作数据
      - 使用了有哪些数据？原有数据有没有发生变化？
        - 这些数据什么作用？
        - 有哪些数据？变了吗？
          - 涉及页面操作吗？
            - 1. 批量操作需要考虑性能，或者测试给出性能指标
            - 2.页面的操作提示合理吗？
            - 3.页面的操作响应时长可接受吗？超过3S了吗？
          - 涉及数据输入吗？
            - 该场景用户操作时，真实的输入数据是什么样的？
          - 涉及数据库表吗？
            - 增删改表了吗？
            - 增删改表中字段了吗？
          - 涉及输出存储到redis中吗？
          - 涉及导入导出数据吗？
            - 1、测试数据构造需全面，覆盖所有数字、字母、符号组合
            - 2.考虑文件的大小问题，文件最大行数、单元格最大字符长度等情况
            - 3.针对例如excel等文件类型，需要测试工具兼容性，如2013等版本
            - 4.优先使用现网数据进行测试，运维提供数据
      - 是否涉及到新增/修改接口？
        - 新增接口
          - XXXX(post/rest/xxx/xxxxxx/v1/xxx-yyyy/xxxxx/zzzzz)
            - 同时也要对单接口测试设计模板来进行分析
        - 修改接口
          - XXXX(post/rest/xxx/xxxxxx/v1/xxx-yyyy/xxxxx/zzzzz)
            - 同时也要对单接口测试设计模板来进行分析
      - 是否涉及数据操作的边界场景？
        - 跨年、跨月场景？如订购跨年、续订跨年等是否会造成影响？
        - 平年、闰年的边界区分？如2.28号，2.29号等
        - 精度区分，如保留几位小数，精度策略、用户展示等
        - 特殊的如话单跨小时、跨天跨月跨年等
        - 特殊的如订单跨小时、跨天跨月跨年等
      - 是否存在现网数据割接？
      - 是否涉及大数据量？是否需要进行性能测试？
        - 提示：若涉及到大数据量场景，如导入导出2000条数据，跨页查询等，也需要在功能测试中覆盖
        - 公共分析维度
          - 接口级，如新增接口，接口变更等
          - 特性级，如支付、订购、登录、初始化、浏览等重要特性方案变更等
          - 使用范围，如用户同时使用；单人重复使用；后台数据库和进程类定时任务
        - 用户对产品的处理能力和响应速度要求如何？
        - 有哪些指标需要满足？
        - 该特性是否是高耗费资源的操作？
        - 该特性是否修改，是否会被频繁使用？
        - 该特性是否修改，是否会被频繁使用？
        - 该特性是否涉及批量处理？
        - 性能专项组是否需要介入测试？
    - 兼容性
      - 场景兼容性
        - 考虑不希望启用该特性的项目，升级后是否会影响老功能，有无兼容老功能的方案
      - 数据兼容性
        - 此流程生成或者修改的数据对象，是否兼容其他流程的使用？
        - 当前的数据对象修改，是否兼容之前已经产生的数据对象？
        - 当时的数据修改，是否涉及到需要和其他服务间的数据同步？
      - 接口兼容性
        - 修改的接口是否考虑了向上兼容？
        - 修改的接口，是否可以兼容所有的调用方
    - 配置参数
      - 有没有变化参数，具体什么参数，参数意义是什么，取值范围呢?
      - 受不受参数影响？受哪些参数影响？参数取值是什么？
      - 参数的默认取值是什么？这样设置是否合理？
      - 配置参数是否可以手工修改？需要的话需要进行边界场景测试吗
    - 是否涉及到和其他特性交互
      - 跟其他特性是否共用了接口，是否互相影响？ 有哪些测试点？
      - 跟其他特性是否共用了关键数据库和文件数据？ 有哪些测试点？
      - 跟其他场景，是否有生命周期上下文的关联性？ 有哪些测试点？
      - 涉及到和其他服务之间的数据同步吗？
    - 可靠性
      - 主要通过接口可靠性来保证，除此之外，是否涉及其他情况？
      - 作为服务提供方，若前一个请求还在处理，又来一个相同请求，会怎么样？
        - 需要做到幂等
        - 调用方的超时时间>被调用方的超时时间
      - ...
    - 安全性
      - 是否涉及口令密钥？
        - 是否加密存储
        - 是否加密传输
      - 是否涉及个人数据
        - 是否加密存储？
        - 是否加密传输？
        - 日志中是否会记录个人数据？
          - 个人敏感数据需要做脱敏处理
        - 涉及的工具和脚本权限是否最小
      - 是否涉及用户通信内容
        - 是否加密存储
        - 是否加密传输
      - 是否涉及非查询操作
        - 是否记录日志
        - 日志中是否包括包含用户ID(包括关联终端、端口、网络地址或通信设备）、时间、事件类型、被访问资源的名称、访问结果
      - 是否满足日志规范要求
        - 日志记录需涵盖所有的用户活动
        - 日志记录需涵盖所有的操作指令
      - ...
    - UI规范
      - 是否满足UI规范？
      - 是否涉及国际化？
        - 针对新客户端的多语言，主要测试：中文、英文？
    - 易用性
      - 是否需要测试用户看到的信息，是否利于可理解
      - 是否需要测试，展现给用户可操作的内容，可以和便于操作？
    - 可服务性
      - 安装
        - 版本安装时，该特性需要哪些测试点？
      - 升级
        - 版本升级时，该特性有哪些测试点？
      - 配置
        - 特性涉及的配置项，有哪些测试点？
      - 资料
        - 该特性需要资料中是否需要补充相关调测和说明？
      - 性能上报
        - 该流程是否涉及到性能上报项的触发
    - 组网
      - 有没有新组网结构的变化，需要哪些测试点？
      - 现网的组网情况，对于该特性有什么使用限制？ 需要哪些测试点？
    - ...
  - 测试覆盖
    - 规范要求
      - 页面测试要求&规范
        - 浏览器兼容性验证要求&方法
          - PC端浏览器兼容性
          - PC端分辨率兼容性
        - 可测试性规则
          - 控件ID要求
          - 阶段性要求：控件有ID的，只能够使用ID捕获控件，不能够使用xPath的方式捕获控件
        - 页面性能测试准则
          - 1、页面大小
            - 以transferred为准
          - 2、页面加载时间
            - 以load为准
          - 3、页面资源
          - 4、页面请求数
          - 5、体验
      - 导出功能测试规范
      - 消息通知基本功能测试准则 
      - 新开发功能资料文档上线流程
    - 测试范围
      - 1、影响因子
        - 用户类型
          - 普通用户
          - 企业主用户
          - 企业子用户
          - 特殊用户场景
        - 付费类型
          - 预付费
          - 后付费
        - 扣费时间
        - 功能入口
        - 计费模式
        - 支付方式
          - 现金支付
          - 代金券抵扣
          - 现金券抵扣
          - 折扣
        - ...
      - 2、数据源信息
      - 3、本次需求涉及的接口
        - 接口文本用例输出情况
        - 接口自动化用例实现情况
      - 4、本次需求涉及的场景
        - 背景
        - 涉及用户
          - 月结用户
        - 涉及站点
          - 中国站
          - 国际站
        - 入口
        - 涉及计费模式
          - 按需
        - 上线模式
        - 大数据检查点
        - 查询/导出接口
      - 5、本次需求涉及的专项测试点
        - 可靠性测试
        - 安全性测试
        - 可服务性测试
    - 反向改进点check
      - 1、功能特性如果仅在中国站上线，需要检查国际站不受影响；如果仅在国际站上线，需要检查中国站不受影响。
      - 2、查询和导出功能，都需要考虑批处理边界值&分页场景。
      - 3、接口传参是TZ时间格式的情况下，一定是UTC时间(北京时间-8)
    - 功能特性上线准入评估
      - 1、测试执行结束，问题单回归完成，无关键遗留问题
      - 2、自动化用例完成情况
      - 3、是否涉及规则改动？是否有资料改动点？
      - 4、页面自动化是否同步调整？
      - 5、上线时间点？开关是否默认打开？是否白名单开放？配置白名单的友好用户名单？
      - 6、页面拨测用例是否同步实现或者更新？
