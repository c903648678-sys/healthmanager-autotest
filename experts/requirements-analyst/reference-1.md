## 三件套分工（生成时如何用）

| 文件 | 角色 | 对用例生成的约束 |
|------|------|------------------|
| **requirements**（主） | 验收 / EARS / 用户故事 / Glossary | **用例条数与预期的唯一主依据**；每条 EARS/AC 至少映射 1 条用例（或显式合并说明） |
| **design**（辅） | 界面结构、模块边界、数据流、风险点 | 用于补全：**入口/控件名、前置数据、断言对象、异常面**；**禁止**把纯内部 API/类名/缓存键写成 UI 步骤，除非需求已规定用户可观察结果 |
| **tasks**（辅） | 实现拆分与完成态 | 标为未做 / TODO / 未排期的能力 → 用例标 **手工或 blocked 备注**，或生成后列入「暂缓自动化」；已完成任务优先进可自动化候选 |

冲突处理：

1. requirements 与 design 不一致 → **以 requirements 为准**，在预览 `warnings` 写出矛盾点  
2. tasks 显示未交付但 requirements 已写验收 → 允许生成用例，但执行方式偏手工/`skeleton`，备注写清「实现未完成」  
3. 仅有 design、无 requirements → `blocked`，要求补需求或用户确认「按 design 临时抽验收」
